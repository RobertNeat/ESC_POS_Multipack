# Plan refaktoryzacji SOLID

Refaktoryzacja zachowuje istniejące przepływy użytkowe. Każdy zakres ma osobne
pliki, kryteria odbioru i testy, aby zmiany można było wdrażać oraz przeglądać
niezależnie.

## Zakres 1: kontrakty i adapter POS-8370

Cel: oddzielić model drukarki od ogólnej abstrakcji urządzenia.

1. Ograniczyć `printer-adapter` do kontraktów niezależnych od protokołu i modelu.
2. Przenieść instrukcje ESC/POS, konfigurację firmware i operacje diagnostyczne
   do `pos-8370-adapter`.
3. Rozdzielić kodowanie instrukcji, tekstu, konfigurację i cykl połączenia na
   jednostki o jednej odpowiedzialności.
4. Zastąpić tekstowe klucze ustawień stabilnymi identyfikatorami.
5. Usunąć ścieżkę zgodności, która mogła tworzyć puste komendy.

Kryteria odbioru: brak pojęć POS-8370 w pakiecie ogólnym, zachowane API
wysokiego poziomu, testy pakietów przechodzą.

## Zakres 2: usługa REST

Cel: rozdzielić transport HTTP od wykonywania zadania drukowania.

1. Wydzielić kolejkę operacji, dekodery danych i mapowanie błędów.
2. Ujednolicić przebieg inicjalizacji, wykonania, przywrócenia trybu i cięcia.
3. Podzielić DTO według funkcji API i zachować jeden punkt eksportu.
4. Mapować repozytorium ustawień na publiczny model bez surowych bajtów.
5. Dodać testy kolejności operacji, kolejkowania i odpowiedzi konfiguracji.

Kryteria odbioru: kontroler deleguje, serwis orkiestruje, małe jednostki realizują
szczegóły; API nie ujawnia komend urządzenia; testy i lint przechodzą.

## Zakres 3: klient Angular

Cel: oddzielić prezentację, komunikację HTTP i stan interfejsu.

1. Przenieść każdy szablon i arkusz stylów do osobnego pliku.
2. Rozdzielić klienta HTTP, stan połączenia, preferencje i powiadomienia.
3. Wydzielić współdzielone opcje fontów, papieru i kodowania.
4. Rozwinąć skondensowane metody do czytelnych bloków.
5. Rozróżnić błąd danych od utraty połączenia.

Kryteria odbioru: brak dużych szablonów i stylów inline, zachowany wygląd oraz
zachowanie, testy komponentów/usług i lint przechodzą.

## Zakres 4: wspólne bramki jakości

Cel: jedna konwencja dla całego monorepo.

1. Ustalić LF, UTF-8 i wspólny format Prettier.
2. Zapewnić polecenia `lint`, `format:check`, `test` i `build` z katalogu głównego.
3. Objąć lintem aplikacje, pakiety, testy i pliki konfiguracyjne.
4. Uruchamiać naprawy formatowania jawnie; zwykły lint nie może zmieniać plików.

Kryteria odbioru: wszystkie cztery polecenia kończą się kodem zero, a drzewo
robocze nie zmienia się po samym sprawdzeniu.

## Kolejność integracji

1. Kontrakty adaptera i publiczne modele.
2. Dopasowanie backendu do nowych interfejsów.
3. Dopasowanie klienta do jawnych kontraktów HTTP.
4. Formatowanie mechaniczne.
5. Lint, testy, build i poprawki regresji.
